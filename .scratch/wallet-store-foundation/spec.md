# Wallet store and ledger persistence foundation

Status: ready-for-agent

## Problem Statement

The payments gateway’s Wallet service has a ledger schema and a minimal HTTP process, but no PostgreSQL connection layer, no sqlc-backed persistence, and no way to create Accounts or post Ledger Transactions safely. Without that foundation, higher-level payment flows cannot rely on a correct, atomic, append-only ledger.

## Solution

Build the Wallet persistence foundation: sqlc queries over the existing ledger schema, a shared PostgreSQL pool, a Wallet store that creates Accounts and posts balanced Ledger Transactions atomically, liveness/readiness endpoints, integration tests against a real database, and graceful shutdown that drains HTTP before closing the pool.

## User Stories

1. As a platform operator, I want the Wallet service to connect to PostgreSQL through a single connection pool at startup, so that database resources are bounded and shared correctly.
2. As a platform operator, I want startup to fail cleanly if PostgreSQL is unreachable, so that I do not run a process that cannot serve ledger work.
3. As a platform operator, I want failed startup to close any partially opened pool, so that connections are not leaked.
4. As a platform operator, I want pool settings to be conservative by default and overridable via environment variables, so that I can tune without code changes.
5. As a platform operator, I want `GET /healthz` to report process liveness without talking to PostgreSQL, so that orchestrators can restart unhealthy processes independently of database outages.
6. As a platform operator, I want `GET /readyz` to succeed only when PostgreSQL is reachable, so that traffic is not sent to a Wallet instance that cannot persist ledger data.
7. As a platform operator, I want `GET /readyz` to fail when the process is shutting down, so that load balancers drain the instance before exit.
8. As a platform operator, I want `GET /readyz` to use a bounded timeout when pinging PostgreSQL, so that readiness checks cannot hang indefinitely.
9. As a platform operator, I want graceful shutdown to mark the process not-ready first, so that new traffic stops before in-flight work finishes.
10. As a platform operator, I want the HTTP server to drain in-flight requests before the PostgreSQL pool is closed, so that those requests do not lose their database connections mid-flight.
11. As a platform operator, I want shutdown to respect a deadline and log failures, so that a stuck drain cannot hang the process forever.
12. As a Wallet developer, I want sqlc configured for PostgreSQL with the pgx/v5 interface, so that generated query code matches the driver’s types.
13. As a Wallet developer, I want schema for codegen kept separate from golang-migrate up/down scripts, so that sqlc inputs stay clean while migrations remain the runtime source of truth.
14. As a Wallet developer, I want sqlc generation to fail loudly on invalid SQL, so that broken queries never ship unnoticed.
15. As a Wallet developer, I want never to edit sqlc-generated code by hand, so that regeneration stays safe and repeatable.
16. As a Wallet developer, I want Account create/get/list-by-owner queries, so that the store can manage Accounts without ad-hoc SQL.
17. As a Wallet developer, I want Account Balance readable via query, so that callers can see derived balances without inventing their own aggregation.
18. As a Wallet developer, I want Ledger Transaction and Entry create queries plus list-by-account and get-transaction / list-entries-by-transaction, so that posting and retrieval are covered.
19. As a ledger writer, I want to create a user Account with an Owner UUID, so that end-user funds have a clear owner association.
20. As a ledger writer, I want to create a System Account with a null Owner, so that platform positions can sit on the ledger without a fake user.
21. As a ledger writer, I want Account Currency fixed as an ISO 4217 alphabetic code, so that every Account has an unambiguous unit.
22. As a ledger writer, I want Amounts expressed as positive minor units, so that money math stays integer-safe.
23. As a ledger writer, I want to set Normal Balance when creating an Account, so that Account Balance semantics match debit-normal or credit-normal accounts.
24. As a ledger writer, I want Account and Ledger Transaction IDs generated by the application as UUIDs, so that I know identifiers before commit and tests stay deterministic.
25. As a ledger writer, I want to post a Ledger Transaction with multiple Entries in one atomic operation, so that partial posts never appear.
26. As a ledger writer, I want posting to reject empty or unbalanced Ledger Transactions before commit when possible, so that I get clear application-level errors.
27. As a ledger writer, I want PostgreSQL to remain the hard authority for balance and non-empty invariants, so that buggy callers cannot commit invalid ledgers.
28. As a ledger writer, I want unbalanced or empty posts to surface as typed store errors, so that callers can distinguish invariant failures from infrastructure failures.
29. As a ledger writer, I want multi-currency Ledger Transactions allowed when each Currency’s debits equal credits, so that cross-currency structural postings remain possible without floating FX inside the ledger.
30. As a ledger writer, I want Entry Currency to match the Account’s Currency via database constraint, so that mismatched money cannot attach to an Account.
31. As a ledger writer, I want a reusable database transaction helper that begins, commits on success, rolls back on error or panic (re-throwing panic), and returns commit errors, so that atomic posting logic is not duplicated.
32. As a ledger writer, I want the ledger to stay append-only, so that corrections are reversing Ledger Transactions rather than updates or deletes.
33. As a ledger reader, I want to retrieve a posted Ledger Transaction and all of its Entries, so that I can audit a single movement of value.
34. As a ledger reader, I want to list Entries for an Account, so that I can inspect that Account’s history.
35. As a ledger reader, I want Account Balance derived from Entries and Normal Balance, so that reported funds match the ledger rather than a cache.
36. As a test engineer, I want HTTP tests that prove `/healthz` does not need a database, so that liveness stays decoupled from Postgres.
37. As a test engineer, I want HTTP tests that prove `/readyz` returns success when the database is reachable and failure when it is not, so that readiness semantics are locked in.
38. As a test engineer, I want Wallet store integration tests against a real PostgreSQL database, so that sqlc, constraints, and transactions are exercised together.
39. As a test engineer, I want integration tests skipped when no test database URL is configured, so that unit-only environments still pass.
40. As a test engineer, I want test data isolated by unique IDs without truncating shared tables, so that tests can run safely in parallel and in any order.
41. As a test engineer, I want a test that forces mid-post failure and asserts no leftover Ledger Transaction or Entries, so that atomicity is proven.
42. As a test engineer, I want a test that rejects an unbalanced Ledger Transaction, so that invariant enforcement is covered end-to-end.
43. As a future service owner, I want the PostgreSQL pool helper under a shared platform module, so that Auth or Transfer can reuse the same connection pattern later.
44. As a future agent, I want an ADR recording that ledger invariants are enforced in PostgreSQL and the ledger is append-only, so that later changes do not casually move those rules into app-only checks.
45. As a domain collaborator, I want glossary language (Account, System Account, Owner, Ledger Transaction, Entry, Amount, Currency, Account Balance) used consistently, so that specs and code do not drift into “wallet” or “transfer” as ledger nouns.

## Implementation Decisions

- Wallet is the service/bounded-context name only; domain nouns are Account, System Account, Owner, Ledger Transaction, Entry, Normal Balance, Currency, Amount, and Account Balance (see root glossary).
- No public HTTP API for Account or Ledger Transaction operations in this work; only `/healthz` and `/readyz`.
- Introduce sqlc with PostgreSQL + pgx/v5; keep a dedicated schema snapshot for codegen alongside query files; keep golang-migrate migrations as the runtime schema source of truth (Makefile migrate targets already exist).
- sqlc-generated code lives in a dedicated Wallet DB package; hand-written Wallet store code lives in the Wallet package; PostgreSQL pool helper lives in a shared platform postgres module.
- sqlc query surface: CreateAccount, GetAccount, ListAccountsByOwner, GetAccountBalance, CreateTransaction, CreateEntry, ListEntriesByAccount, GetTransaction, ListEntriesByTransaction.
- Hand-written store orchestrates posting: a Post Ledger Transaction operation calls CreateTransaction and CreateEntry inside the shared in-transaction helper; callers do not assemble posts from raw Entry inserts.
- Get Account Balance reads the existing derived balances view; no cached balance column on Account.
- Owner is an opaque Auth UUID; null Owner means System Account; no local User table in Wallet.
- Application generates UUIDs for Account and Ledger Transaction IDs; database defaults remain as backup only.
- Amounts are positive integers in minor units; Account Currency is ISO 4217 alpha-3 and fixed for the Account’s lifetime; a Ledger Transaction may include multiple Currencies if each Currency balances.
- Go pre-validates non-empty and per-Currency debit/credit equality; PostgreSQL deferred constraint trigger remains authoritative; map check violations to typed store errors.
- Edit the initial ledger migration in place (acceptable: no production data): fix the balance-trigger table-name branch, add default timestamp on Ledger Transaction created-at, clean known comment typos; operators will recreate the volume/database.
- Wire a single pool in the Wallet process entrypoint from required `DATABASE_URL`, with optional conservative pool env overrides; keep listen address `:8081` for now; ping on startup; inject pool/store into handlers; close pool after HTTP shutdown.
- Readiness combines DB ping and an explicit not-ready-on-shutdown gate.
- Record ADR: PostgreSQL-enforced ledger invariants and append-only ledger (reversing Ledger Transactions only).
- Dependencies: jackc/pgx/v5 and google/uuid (plus sqlc toolchain for generation).

## Testing Decisions

- Good tests assert external behavior (HTTP status/body semantics; store inputs/outputs and persistence outcomes), not sqlc internals, SQL string contents, or private helpers.
- Seams (confirmed):
  1. Wallet store against real PostgreSQL — primary seam for Account creation, posting, retrieval, balance, reject, and rollback.
  2. HTTP handler wiring with injectable pool and readiness gate — secondary seam for `/healthz` and `/readyz`.
- No third seam: do not unit-test the pool or generated sqlc package in isolation.
- Integration tests use `TEST_DATABASE_URL` and skip when unset; isolate with unique UUIDs; no truncates of shared tables; provoke rollback via mid-transaction constraint/FK failure and assert absence by ID.
- Cover at least: user Account create; System Account with null Owner; successful balanced post; unbalanced reject; atomic rollback on failure; retrieve Ledger Transaction with Entries; health without DB; ready success and failure paths.
- Prior art: none in-repo yet (greenfield tests for this service).

## Out of Scope

- REST (or other) APIs to create Accounts, post Ledger Transactions, or read balances/history over HTTP.
- Auth service integration beyond storing opaque Owner UUIDs.
- Transfer service, payment orchestration, FX conversion, or fee engines.
- Balance caching, materialised balance tables, or denormalised running balances.
- Updating or deleting ledger rows; account closure/rename workflows; pagination APIs.
- Redis/NATS usage; multi-tenant beyond Owner UUID; migrations framework replacement.
- Seeding predefined System Accounts.
- Changing listen address configuration (remains hardcoded for this foundation).

## Further Notes

- Domain vocabulary lives in the root glossary under the Wallet context; keep implementation and ADR language aligned with it.
- After implementation: run sqlc generate, format/static checks if available, unit tests, integration tests when a test DB is present, and a manual smoke of startup / health / ready / graceful shutdown.
- Operators wiping local Docker volume after the in-place migration edit is expected and already accepted.
- sqlc schema snapshot and migrations must be kept in sync by hand until a later automation exists; do not invent that automation in this spec.
